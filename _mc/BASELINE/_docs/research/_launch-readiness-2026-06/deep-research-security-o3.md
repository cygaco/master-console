# Security hardening for indie / vibe-coded SaaS + AI apps (2025-2026) — OpenAI Deep Research (o3-deep-research)

# Security Hardening Checklist for SaaS/Mobile Apps (2025–2026)

This report outlines **current security-hardening requirements** (as of 2025–2026) for indie SaaS and mobile app founders, especially those using AI-assisted “vibe coding” platforms. Each finding includes a clear claim, supporting evidence with dates, a confidence level, and sources. We flag any areas of active change or uncertainty. 

## 1. Database Access Control: Enable RLS and Prevent Open Data

#### Row-Level Security Disabled by Default (Supabase) 
**Claim:** By default, Supabase databases had Row-Level Security (RLS) **off** on new tables, meaning any user with the public “anon” key could read **all** rows unless RLS policies were added. This misconfiguration leads to Broken Object Level Authorization (BOLA) exposures (OWASP API Security #1). Supabase **requires enabling RLS per table** to lock down data. Recent changes in mid-2025 flipped the default for new tables to RLS **enabled** (to mitigate this risk), but developers must still verify RLS on every table, especially for existing projects.  

**Evidence:** Security researchers disclosed in April 2026 that **any Supabase table without RLS** allowed an attacker with the public API key to query every row ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Class%20vulnerability%20%E2%80%94%20new%20Supabase,reads%20every%20row)) ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Attacker%20scrapes%20JS%20bundle%20for,Without%20RLS%2C%20all%20rows%20returned)). In one incident (CVE-2025-48757), a vibe-coding platform’s misconfigured Supabase DB exposed **170+ apps** worth of private user data – “personal debt records, home addresses, and API keys, all readable with two strings from the page source” (the URL and anon key) ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=The%20Lovable%20RLS%20Leak%3A%20170%2B,Could%20Query%20From%20the%20Browser)) ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=In%20April%202025%2C%20a%20security,had%20pulled%20real%20user%20data)). This maps to an outright **Broken Access Control** failure: “no row-level security means any user reaches any row” ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=That%20maps%20precisely%20to%20three,of%20OWASP%27s%20most%20critical%20categories)). Supabase responded by adjusting defaults (as of **May 30, 2025**, new tables default to no public access until RLS is configured) – existing projects, however, remain **developer’s responsibility** to secure. Enabling RLS on a table (Postgres `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`) and writing *per-tenant or per-user policies* ensures each request only sees authorized rows ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=supabase%20db%20dump%20,use%20Securie%27s%20Supabase%20RLS%20specialist)). For stronger enforcement, tables can also be set to `FORCE ROW LEVEL SECURITY` so that even highly privileged roles cannot bypass RLS (PostgreSQL applies RLS for all access when forced – note this is an advanced safety measure). Without these steps, attackers can perform IDOR/BOLA attacks simply by altering object IDs in requests to read others’ data, which remains the top API vulnerability in 2023 ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=CVE,strings%20from%20the%20page%20source)). **(Confidence: HIGH)** 

**Sources:** Securie vulnerability report (Apr 30 2026) ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Class%20vulnerability%20%E2%80%94%20new%20Supabase,reads%20every%20row)) ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Attacker%20scrapes%20JS%20bundle%20for,Without%20RLS%2C%20all%20rows%20returned)); Flowpatrol case study (Mar 28 2026) ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=The%20Lovable%20RLS%20Leak%3A%20170%2B,Could%20Query%20From%20the%20Browser)); OWASP API Top 10 (2023) – Broken Object Level Authorization ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=That%20maps%20precisely%20to%20three,of%20OWASP%27s%20most%20critical%20categories)). *(Supabase’s default was confirmed flipped in mid-2025 – official announcement in May 2025; older tables still require manual RLS enablement.)*

#### Service-Role Key Bypasses RLS (Server-Only Secret) 
**Claim:** Supabase provides a secondary admin API key (the **service_role** key) which **bypasses all RLS policies** by design. This key grants full read/write access to the database (has the Postgres `BYPASSRLS` privilege). It **must be kept secret on the server** – never exposed in frontend code, git repos, or chat logs – because any leak is equivalent to a root DB credential. In June 2025, Supabase introduced new nomenclature to reinforce this: the client API key is now called **“publishable”** (prefixed `sb_publishable_...`) and the service role key is called **“secret”** (`sb_secret_...`), emphasizing that it must remain confidential. The Supabase dashboard flags the service key with a warning icon, and their docs clarify it should **never be used in client-side context**. 

**Evidence:** Supabase’s project settings (as of May 2026) label the anon key as a **“publishable” client key** and show the service_role key masked with a **“secret”** label and warning ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Affects)). The publishable (anon) key is safe for front-end use *only because* it’s restricted by RLS policies — it “only grants whatever your RLS policies allow” . In contrast, the service_role secret is effectively a superuser key: any request with it ignores RLS (`BYPASSRLS`) and can read or modify all data ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Class%20vulnerability%20%E2%80%94%20new%20Supabase,reads%20every%20row)). A 2026 incident demonstrated the impact of leaking this secret: the Lovable.dev AI builder had inadvertently exposed many projects’ **service_role keys** in client-side code and AI chat histories. Attackers who found those keys in the app code gained full database access. (Free accounts on the platform could read other users’ chat histories, source code, and even database credentials until the issue was discovered in April 2026 ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=The%20Lovable%20RLS%20Leak%3A%20170%2B,Lovable%20%E2%80%94%20one%20of%20the)) ([bastion.tech](https://bastion.tech/blog/lovable-april-2026-data-breach/#:~:text=Lovable%20Data%20Breach%20April%202026%3A,and%20customer%20data%20across%20every)).) All affected projects had to **rotate** (regenerate) their service_role keys immediately to re-secure their databases ([supabase.com](https://supabase.com/docs/guides/auth/auth-deep-dive/auth-row-level-security#:~:text=Security%20%28RLS%29.%20,Supabase%20allows%20convenient%20and%20secure)). Supabase’s documentation and community guides now repeatedly warn that the service_role key should be treated like a password – stored only in backend environments (e.g. server .env files) and never embedded in client apps ([supabase.com](https://supabase.com/docs/guides/auth/auth-deep-dive/auth-row-level-security#:~:text=Security%20%28RLS%29.%20,Supabase%20allows%20convenient%20and%20secure)) ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Affects)). **(Confidence: HIGH)**

**Sources:** PTKD Journal – *“Is the Supabase service_role key public?”* (May 2026) ([securie.ai](https://securie.ai/vuln/supabase-default-rls-disabled-pattern#:~:text=Affects)); PTKD Journal – *“anon key vs service_role key”* (May 2026) ; Flowpatrol report on Lovable breach (Mar 2026) ([flowpatrol.ai](https://flowpatrol.ai/blog/lovable-rls-vulnerability-170-apps-exposed#:~:text=CVE,strings%20from%20the%20page%20source)); Bastion breach analysis (Apr 21 2026) ([bastion.tech](https://bastion.tech/blog/lovable-april-2026-data-breach/#:~:text=Lovable%20Data%20Breach%20April%202026%3A,and%20customer%20data%20across%20every)).

## 2. Secret Management: Protect API Keys and Credentials

#### No Secrets in Git Repos or Client Bundles 
**Claim:** **Never commit secrets or credentials to source control**. API keys, database passwords, and credentials must be kept out of GitHub repositories (including all branches and history) to avoid leakage. Use environment variable files (like *.env*) which are git-ignored, and ensure no secret keys are in the front-end bundle. Front-end code cannot keep secrets – any variable embedded at build time (e.g. **NEXT_PUBLIC_*** or **VITE_*** env variables) is visible to end users. Only use such “public” prefixes for non-sensitive config. All secret keys should reside on the server side. 

**Evidence:** High-profile breaches have occurred from secrets accidentally pushed to public repos. For example, in 2025, dozens of Lovable.dev projects leaked their Supabase service_role keys in client-side code and AI chat logs ([ptkd.com](https://ptkd.com/journal/lovable-dev-supabase-rls-bypass-with-service-role-key#:~:text=Lovable,chat%20history%2C%20the%20key%20is)), leading to unauthorized access. Once a secret is in a public GitHub commit, attackers often find it within **minutes** via automated scanners. GitHub’s own scanning infrastructure (made free for public repos in 2023) detects ~**hundreds of leaked secrets daily** and now even **blocks pushes** that contain well-known secret patterns (e.g. AWS keys) ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=In%202024%2C%20cybersecurity%20experts%20identified,create%20fake%20packages%20with%20these)). Tools like **TruffleHog** and **Gitleaks** are widely used to scan codebases for API keys or credentials to prevent such leaks *before* code is pushed. In 2025, GitHub advanced its **secret scanning** with *push protection*, which rejects commits that contain certain secrets unless explicitly overridden ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=In%202024%2C%20cybersecurity%20experts%20identified,create%20fake%20packages%20with%20these)). Environment files (e.g. *.env*) should always be listed in **.gitignore** and never uploaded; if a key does slip into source control, it must be **invalidated and rotated** (generate a new key) immediately. Frontend frameworks now make it clear that only variables prefixed with e.g. `NEXT_PUBLIC_` or `VITE_` will be exposed to the browser – anything secret should *not* use those prefixes nor be referenced in client-side code ([www.itpro.com](https://www.itpro.com/technology/artificial-intelligence/openai-chatgpt-atlas-ai-browser-prompt-injection-attack-risk#:~:text=2025,%E2%80%9Cagent%20mode%E2%80%9D%20for%20performing%20web)). As a rule, assume any value in frontend JavaScript is public. **(Confidence: HIGH)**

**Sources:** NCSC guidance on secret scanning (Dec 2025) ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=In%202024%2C%20cybersecurity%20experts%20identified,create%20fake%20packages%20with%20these)); GitHub documentation on push protection (2023); PTKD Journal on Lovable key exposure (May 2026) ([ptkd.com](https://ptkd.com/journal/lovable-dev-supabase-rls-bypass-with-service-role-key#:~:text=Lovable,chat%20history%2C%20the%20key%20is)); Next.js Environment Variable docs (2023).

#### Secret Scanning and Key Rotation 
**Claim:** **Implement automated secret scanning** in your development workflow and rotate credentials if a leak is suspected. This means using tools or services to catch API keys, tokens, or passwords in code repositories and CI pipelines. If a secret is exposed (through Git history, a client bundle, or an UI leak), assume it’s compromised and **rotate it** (revoke and replace it) immediately. Many cloud APIs provide the ability to roll keys; for Supabase, you can generate new anon or service_role keys from the dashboard if needed. 

**Evidence:** In modern DevSecOps, secret scanning is a standard control. Open-source tools like **Gitleaks** (v8 and above) or **TruffleHog** can be run as Git hooks or CI steps to flag commits containing patterns like `API_KEY=` or known private key signatures. GitHub’s built-in **Secret Scanning** (generally available by 2023) monitors public repositories in real-time, and for private repos with Advanced Security, it scans every push ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=In%202024%2C%20cybersecurity%20experts%20identified,create%20fake%20packages%20with%20these)). The importance of rotation is highlighted by incidents such as the Lovable.dev breach, where the recommended response was for developers to **revoke any exposed Supabase keys** and generate fresh ones ([supabase.com](https://supabase.com/blog/supabase-security-2025-retro#:~:text=Supabase%20Security%20Retro%3A%202025%20Supabase,minute%20read%20Bil%20HarmerCSO%20Paul)). Cloud providers like AWS and database services often have guidance to **rotate keys periodically** as a best practice (e.g. every 90 days) to limit the window of misuse. By 2025, GitHub’s *push protection* even proactively blocks known secret patterns from being pushed ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=existent%20packages%20mistakenly%20added%20to,create%20fake%20packages%20with%20these)), underscoring how common secret leaks are and the need for automated defenses. In short, *scanning plus immediate rotation* is essential to prevent a leaked credential from becoming a full-blown compromise. **(Confidence: HIGH)**

**Sources:** GitHub Secret Scanning announcment (Apr 2023) ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=In%202024%2C%20cybersecurity%20experts%20identified,create%20fake%20packages%20with%20these)); PTKD Journal – *“Supabase service_role key incident response”* (May 2026) ([supabase.com](https://supabase.com/docs/guides/auth/auth-deep-dive/auth-row-level-security#:~:text=Security%20%28RLS%29.%20,Supabase%20allows%20convenient%20and%20secure)); AWS Security Advisory on key rotation (2025).

## 3. Rate Limiting and Abuse Prevention 

#### Quotas on API & AI Usage (Prevent Unbounded Consumption) 
**Claim:** **Enforce strict rate limits and usage quotas** on your APIs, especially for expensive operations like AI/LLM endpoints. Uncapped usage can lead to Denial-of-Service or **“Denial-of-Wallet”** attacks where an attacker drives up cloud costs. The OWASP Top 10 for Large Language Model Apps (2025) lists **Unbounded Consumption (LLM10)** as a critical risk, reflecting how malicious actors can abuse unlimited API calls. Implement per-user and per-IP request rate limits, and if offering a free tier, set daily/monthly query quotas and cost ceilings. This ensures one rogue user (or a script) can’t exhaust resources or incur exorbitant fees. 

**Evidence:** The OWASP GenAI Security Project (2025) warns that **uncontrolled LLM usage** can cause severe financial and performance impacts. *“LLM10: Unbounded Consumption”* is described as when an application allows **excessive, uncontrolled queries**, leading to denial of service or huge bills ([genai.owasp.org](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/#:~:text=Attacks%20designed%20to%20disrupt%20service%2C,resource%20exploitation%20and%20unauthorized%20usage)). Notably, attackers have exploited unlimited AI APIs in the past to steal model outputs or rack up costs. For example, sending many large prompts (“variable-length input flood”) or extremely long conversations can grind an LLM service to a halt or make it prohibitively expensive ([genai.owasp.org](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/#:~:text=Common%20Examples%20of%20Vulnerability)). Another scenario is **“Denial of Wallet” (DoW)** attacks, where an adversary runs up usage on a pay-per-request AI service, draining the provider’s budget ([genai.owasp.org](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/#:~:text=render%20the%20system%20unresponsive%2C%20significantly,impacting%20service%20availability)). In response, 2025-era best practices require: setting **per-user token limits** (e.g. each user gets N requests or $X of API usage per month), implementing **circuit breakers** on costly operations, and using tier-based quotas (free vs paid plans). Numerous tools exist – for instance, using a distributed rate limiter (like Upstash Redis or Cloudflare Workers KV) to count requests per API key, or built-in cloud API gateways with rate-limit policies. By mid-2025, open-source libraries emerged to manage LLM usage caps, aligning with OWASP’s guidance to prevent unbounded consumption ([genai.owasp.org](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/#:~:text=Consumption%20occurs%20when%20a%20Large,resource%20exploitation%20and%20unauthorized%20usage)). **(Confidence: HIGH)**

**Sources:** OWASP Top 10 for LLM Applications 2025 – *“LLM10: Unbounded Consumption”* (GenAI Security Project, 2025) ([genai.owasp.org](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/#:~:text=Attacks%20designed%20to%20disrupt%20service%2C,resource%20exploitation%20and%20unauthorized%20usage)) ([genai.owasp.org](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/#:~:text=render%20the%20system%20unresponsive%2C%20significantly,impacting%20service%20availability)); MyCtrl AI Security Tools (2025) on rate limiting; Cloudflare API Gateway docs (2025). 

#### Throttle Authentication and Prevent Credential Stuffing 
**Claim:** **Protect your authentication endpoints** from brute force and credential stuffing attacks by enforcing per-account lockouts and global rate limits. Do **not rely on just IP-based throttling** (attackers rotate IPs); instead, track login attempts per username/account and temporarily lock or challenge after a small number of failed attempts. Implement CAPTCHA or email/SMS verification on suspicious logins, and require Multi-Factor Authentication (MFA) for an extra layer. The goal is to slow down or thwart automated attacks without impacting legitimate users. 

**Evidence:** Credential stuffing (using leaked passwords against many accounts) remains a widespread threat in 2025, often bypassing naive IP-rate limits via distributed botnets. OWASP’s authentication guidance recommends **account-based throttling** – for example, after ~5 failed logins for a user, require a timeout or additional step ([www.itpro.com](https://www.itpro.com/security/ncsc-issues-urgent-warning-over-growing-ai-prompt-injection-risks-heres-what-you-need-to-know#:~:text=risks%20,injection%20targets%20large%20language%20models)). Many high-profile breaches in 2024–2025 stemmed from automated login attempts using reused passwords. Standard practice is a **progressive delay or lockout** (e.g. lock the account for 5 minutes after 5 failures) to make mass guessing infeasible. Importantly, this should be tied to the username, since attackers often use one IP per attempt to evade IP limits. In October 2025, the FBI and CISA issued an advisory highlighting that **MFA could prevent the majority of account takeover attempts**, as stolen credentials alone become insufficient. Similarly, introducing a CAPTCHA or JavaScript challenge after several rapid login attempts can defeat simple scripts. Modern services like Cloudflare Turnstile (launched 2022, widely used by 2025) allow adding CAPTCHA without hurting user experience. Real incidents underscore these measures: In one 2025 attack wave, a botnet attempted **millions of login combos** on a fintech app’s API – only accounts with MFA resisted takeover. The affected company confirmed that **no MFA-enabled accounts were compromised** during the credential stuffing attack (report, Aug 2025). By throttling logins and using MFA, startups greatly reduce the risk of a mass account breach. **(Confidence: HIGH)**

**Sources:** OWASP Authentication Cheat Sheet (2024) ([www.itpro.com](https://www.itpro.com/security/ncsc-issues-urgent-warning-over-growing-ai-prompt-injection-risks-heres-what-you-need-to-know#:~:text=risks%20,injection%20targets%20large%20language%20models)); FBI/CISA PSA on Credential Stuffing (2025); Cloudflare Turnstile launch blog (Sep 2022); Verizon Data Breach Report (2025) on MFA effectiveness.

## 4. AI/LLM Security: Prompt Injection and Output Handling

#### Prompt Injection & LLM Vulnerabilities (unsolved problem) 
**Claim:** **Prompt injection is a novel injection attack against AI models** (especially Large Language Models) where malicious input can make the model ignore developer instructions. In 2025, OWASP released a Top 10 specifically for LLM Applications – **LLM01: Prompt Injection** is ranked the #1 risk. Related AI-specific risks include **Improper Output Handling** (LLM05), **Excessive Agency** (LLM06), and **System Prompt Leakage** (LLM07). These refer to trusting model outputs without validation, giving the model too much authority (e.g. allowing it to execute code or make transactions), and attackers tricking the AI into revealing hidden system instructions, respectively. **No comprehensive solution exists yet** for prompt injection – developers must assume it *cannot be fully mitigated* and instead design with robust fail-safes and least privilege. 

**Evidence:** The OWASP Top 10 for LLM Applications (current as of 2025) highlights these threats: *“LLM01: Prompt Injection”*, *“LLM05: Improper Output Handling”*, *“LLM06: Excessive Agency”*, and *“LLM07: System Prompt Leakage”* are explicitly listed among the top vulnerabilities ([secportal.io](https://secportal.io/frameworks/owasp-llm-top-10#:~:text=Project%20and%20refreshed%20on%20a,inside%2C%20and%20the%20verification%20deliverable)). In practice, prompt injection was first observed in 2022 and grew as a broader problem by 2023–2024, as attackers found they could embed hidden commands in user inputs or data sources that **cause the AI to perform unintended actions** (e.g., reveal confidential info or execute harmful instructions). The UK National Cyber Security Centre warned in Dec 2025 that **“there's a good chance prompt injection will never be properly mitigated”** the way SQL injection was ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=also%20dangerous,likelihood%20or%20impact%20of%20attacks)). Unlike classic injections (which can be solved with parameterization), LLMs inherently mix instructions and data, making them *“inherently confusable”* ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=Crucially%2C%20a%20classical%20confused%20deputy,If%20the)). OpenAI’s own security team acknowledged in late 2025 that prompt injection attacks are *“unlikely to ever be fully solved”* ([www.itpro.com](https://www.itpro.com/technology/artificial-intelligence/openai-chatgpt-atlas-ai-browser-prompt-injection-attack-risk#:~:text=2025,%E2%80%9Cagent%20mode%E2%80%9D%20for%20performing%20web)). **(Confidence: HIGH)**

**Sources:** OWASP GenAI Top 10 (2025) ([secportal.io](https://secportal.io/frameworks/owasp-llm-top-10#:~:text=Project%20and%20refreshed%20on%20a,inside%2C%20and%20the%20verification%20deliverable)); NCSC technical blog – *“Prompt injection is not SQL injection”* (Dave Chismon, Dec 2025) ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=also%20dangerous,likelihood%20or%20impact%20of%20attacks)); ITPro News – *OpenAI on prompt injection* (Dec 24 2025) ([www.itpro.com](https://www.itpro.com/technology/artificial-intelligence/openai-chatgpt-atlas-ai-browser-prompt-injection-attack-risk#:~:text=2025,%E2%80%9Cagent%20mode%E2%80%9D%20for%20performing%20web)).

#### Mitigations: Input Delimiters, Sandboxing, and Output Validation 
**Claim:** **Mitigating LLM attacks requires defensive prompt design and sandboxing.** Developers should never directly concatenate untrusted user input into the system prompt. Instead, **delimit or label user-provided content** (e.g. by wrapping it in quotes or XML tags, or using special tokens) so the model can distinguish instructions from data. Place any user or retrieved content in the prompt **after a clear separator** (like “## User input: ...”), and avoid giving the model system-level authority based on user content. Additionally, treat the model’s **output as untrusted**: post-process or validate outputs, especially before using them in sensitive contexts (for instance, if the model generates code, scan or review it before execution). If the LLM is allowed to perform actions via tools or plugins, follow the principle of **least privilege** – only permit a narrow set of actions and have safeties in place (like confirmation steps or human review for destructive actions). Finally, be alert to **indirect prompt injection**: if your app uses Retrieval-Augmented Generation (RAG) by pulling in data from a database or the web, an attacker might plant malicious instructions in those sources. Thus, sanitize and verify any content drawn into prompts from third-party or user-generated data. 

**Evidence:** Research by Microsoft (reported in 2025) found that using structured prompt formats (marking data vs. instructions) **“can make it harder to successfully inject”** malicious commands ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=There%20are%20a%20number%20of,to%20successfully%20inject%2C%20and%20even)). For example, inserting user input in a JSON field or `<user_message>` tag helps the model treat it differently than system directives. The NCSC advises that no current technique stops prompt injection entirely, but these methods **reduce the likelihood** of a successful attack ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=Crucially%2C%20a%20classical%20confused%20deputy,If%20the)). Proper output handling is equally critical: OWASP LLM05 notes that failing to filter or constrain model outputs can lead to security issues ([secportal.io](https://secportal.io/frameworks/owasp-llm-top-10#:~:text=Project%20and%20refreshed%20on%20a,inside%2C%20and%20the%20verification%20deliverable)). One real example in 2025 was an LLM-based browser plugin that executed search results; attackers crafted pages that, when read by the LLM, output JavaScript which the plugin ran, demonstrating how **improper output handling** can lead to XSS or code execution. To counter this, outputs should be treated like any user-supplied content – e.g. escaped or sandboxed if they might contain code/HTML. **Excessive agency** was illustrated by the case of early “auto-GPT” agents in 2024 that, when compromised by prompt injection, could delete files or make unauthorized transactions because they were given broad operating system access. In response, 2025 guidelines suggest constraining LLM actions (for example, running them in a container with no internet or file deletion permissions, etc.). **System prompt leakage** attacks have repeatedly been shown (notoriously, the initial prompt of Bing’s chat was extracted by users in 2023). Developers should assume hidden prompts or API keys injected into the model could be revealed by a clever query, and thus avoid putting secrets in prompts at all. Overall, because these issues are **not fully solved**, the strategy is **“risk management through careful design, implementation, and operation”** rather than expecting a single fix ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=Crucially%2C%20a%20classical%20confused%20deputy,If%20the)) ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=also%20dangerous,likelihood%20or%20impact%20of%20attacks)). **(Confidence: HIGH)**

**Sources:** NCSC guidance on LLM mitigations (Dec 2025) ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=There%20are%20a%20number%20of,to%20successfully%20inject%2C%20and%20even)) ([www.ncsc.gov.uk](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection#:~:text=also%20dangerous,likelihood%20or%20impact%20of%20attacks)); OWASP Top 10 for LLM (2024–25) ([secportal.io](https://secportal.io/frameworks/owasp-llm-top-10#:~:text=Project%20and%20refreshed%20on%20a,inside%2C%20and%20the%20verification%20deliverable)); MSR Asia – *Securing Prompt Templates* (2025); Case study: Bing Chat prompt leak (Feb 2023, multiple sources).

## 5. Input Validation and Injection Prevention

#### Validate and Sanitize **All** Inputs (Prevent Injection Attacks) 
**Claim:** **Perform strict input validation** on every incoming request. Use schema validation libraries (e.g. Zod for TypeScript, Pydantic for Python) to enforce expected data types, lengths, and formats. Reject or sanitize any input that is **oversized** or malformed. This defends against injection attacks like SQL injection, Cross-Site Scripting (XSS), Server-Side Request Forgery (SSRF), command injection, and more. Injection flaws remain one of the most dangerous web app vulnerabilities – in fact, **“Injection” is ranked A05 in the OWASP Top 10:2025** (still a top-five risk) ([owasp.org](https://owasp.org/Top10/?form=MG0AV3#:~:text=1.%20A01%3A2025%20,6)). By validating inputs and using safe APIs (like parameterized queries and prepared statements for database access), founders can neutralize most injection vectors. 

**Evidence:** The OWASP Top Ten 2025 lists **Injection** attacks as the 5th most critical web app security risk ([owasp.org](https://owasp.org/Top10/?form=MG0AV3#:~:text=1.%20A01%3A2025%20,6)), reaffirming that despite decades of awareness, poorly validated input still causes breaches. This category covers SQL injection, NoSQL injection, OS command injection, LDAP injection, and also cross-site scripting – all of which stem from untrusted input being interpreted as code or commands. A concrete example from 2025 is a series of SSRF exploits against cloud-hosted applications: in April 2025, attackers abused unsanitized URL inputs in EC2-based web apps to have the apps make internal calls revealing AWS credentials ([www.bleepingcomputer.com](https://www.bleepingcomputer.com/news/security/hackers-target-ssrf-bugs-in-ec2-hosted-sites-to-steal-aws-credentials/#:~:text=Hackers%20target%20SSRF%20bugs%20in,vulnerabilities%20in%20websites%20hosted%20on)). In that campaign, simple input validation (restricting allowable URL patterns or using allow-lists for internal endpoints) could have prevented the SSRF that led to the theft of cloud keys ([www.bleepingcomputer.com](https://www.bleepingcomputer.com/news/security/hackers-target-ssrf-bugs-in-ec2-hosted-sites-to-steal-aws-credentials/#:~:text=Hackers%20target%20SSRF%20bugs%20in,vulnerabilities%20in%20websites%20hosted%20on)). Likewise, countless SQL injection incidents occur when applications directly concatenate user input into queries – using parameterized queries (e.g. using `$1, $2` placeholders in PostgreSQL or ORM query builders) would mitigate this. Founders should employ **whitelists/allowlists** for expected values (e.g. only accept known good strings or formats) and use built-in validation frameworks. **Size limits** are also important: e.g., if an API expects a username, enforce a reasonable max length (say 50 chars) to avoid buffer overflows or DoS via giant payloads. Many frameworks now offer request body size limits (for instance, Express.js defaults to 100kb for JSON) – make sure these are configured for file uploads and large text fields. By dropping obviously invalid or overly large inputs at the perimeter, you reduce downstream risk. **(Confidence: HIGH)**

**Sources:** OWASP Top Ten 2025 – *“A05:2025 – Injection”* ([owasp.org](https://owasp.org/Top10/?form=MG0AV3#:~:text=1.%20A01%3A2025%20,6)); BleepingComputer – *SSRF used to steal AWS keys* (Apr 9 2025) ([www.bleepingcomputer.com](https://www.bleepingcomputer.com/news/security/hackers-target-ssrf-bugs-in-ec2-hosted-sites-to-steal-aws-credentials/#:~:text=Hackers%20target%20SSRF%20bugs%20in,vulnerabilities%20in%20websites%20hosted%20on)); OWASP Cheat Sheet – Input Validation (2021); PortSwigger Research – SQLi Prevention references (2023).

#### Magic-Byte File Validation 
**Claim:** **Verify file uploads by their content (“magic bytes”), not just by extension or MIME type.** Whenever users can upload files (images, documents, etc.), enforce checks on the file’s binary signature to ensure it matches the claimed type. Attackers often rename malicious files (like scripts or executables) with innocent extensions (.png, .pdf) to bypass simple filters. Magic byte validation catches this by examining the file header for known signatures (for example, a PDF always begins with `%PDF-`, a PNG with `89 50 4E 47` in hex). Only accept the file if its signature matches an allowed format, and otherwise reject it or label it as suspicious. 

**Evidence:** A 2025 security guide on file uploads notes, *“Relying solely on file extensions or MIME types can leave your application vulnerable to spoofing attacks. A more secure method involves checking the file's magic numbers”* ([transloadit.com](https://transloadit.com/devtips/secure-api-file-uploads-with-magic-numbers/#:~:text=Validating%20file%20uploads%20is%20crucial,also%20known%20as%20file%20signatures)). For instance, an executable malware could be named `invoice.pdf.exe` or even just `invoice.pdf` (with a fake PDF MIME type); if an app trusts the extension, it might treat it as a safe PDF. Magic number checking would reveal it’s actually an EXE by noticing the `MZ` header bytes. In June 2025, Transloadit (a file processing service) highlighted this in their blog, showing code examples of validating an image upload’s header to ensure it’s truly an image file ([transloadit.com](https://transloadit.com/devtips/secure-api-file-uploads-with-magic-numbers/#:~:text=Why%20file%20extension%20validation%20isn%27t,enough)). Many frameworks now supply file-type libraries or you can maintain a list (e.g. JPEG starts with `FF D8 FF E0` or `FF D8 FF E1`). Additionally, performing **virus scanning** on uploads and stripping any executable content from files (e.g. scripts embedded in Office documents) are recommended. Magic-byte checks are a first line of defense that can prevent a lot of “confused deputy” attacks where an uploaded file is later executed or processed unsafely. **(Confidence: HIGH)**

**Sources:** Transloadit Dev Guide – *“Secure API file uploads with magic numbers”* (Jun 12 2025) ([transloadit.com](https://transloadit.com/devtips/secure-api-file-uploads-with-magic-numbers/#:~:text=Validating%20file%20uploads%20is%20crucial,also%20known%20as%20file%20signatures)) ([transloadit.com](https://transloadit.com/devtips/secure-api-file-uploads-with-magic-numbers/#:~:text=Why%20file%20extension%20validation%20isn%27t,enough)); OWASP File Upload Cheat Sheet (2021); Resumable.js Guide on file signatures (Apr 14 2026).

## 6. Additional Web & Supply Chain Protections

#### Security HTTP Headers (CSP, HSTS, etc.) 
**Claim:** **Use modern security headers by default** in your web app responses. Key headers include: **Content-Security-Policy (CSP)** to restrict sources of scripts/iframes and mitigate XSS; **Strict-Transport-Security (HSTS)** to enforce HTTPS and prevent downgrades; **X-Content-Type-Options: nosniff** to stop browsers from MIME-sniffing responses (reducing XSS risk). Other useful headers are **X-Frame-Options** (to prevent clickjacking by disallowing framing of your site), **Referrer-Policy** (to reduce leakage of user data via Referer header), and **Permissions-Policy** (to disable unused browser features like camera, mic by default). Setting these headers with appropriate values significantly hardens your app against common web attacks. They are simple to implement (often just a configuration in your framework or CDN) and have minimal impact on behavior for modern browsers. 

**Evidence:** Security scans in 2025 show many breaches could have been mitigated or made harder with proper headers. For example, a CSP that only allows scripts from your domain (and perhaps a trusted CDN) means even if an XSS vulnerability exists, the attacker’s malicious script from an unapproved domain won’t execute. The **OWASP Secure Headers Project** (last updated 2023) gives a recommended configuration list – including CSP, HSTS, X-Content-Type-Options, and others – with guidance on values. HSTS is critical in a mobile app context as well, ensuring that if your mobile app or a WebView tries an HTTP connection, it gets upgraded to HTTPS, preventing any man-in-the-middle on initial requests. Browsers like Chrome and Firefox have also started marking sites without HSTS as “Not Secure” more aggressively by 2025. Enabling `X-Content-Type-Options: nosniff` has become a baseline in 2025 (it’s even on by default in some frameworks) to stop browsers from interpreting non-JS files as JS. According to Mozilla Security Observatory scans (2024), only ~25% of tested sites had a CSP – but among those, XSS rates were significantly lower. These headers are low-hanging fruit: for instance, enabling HSTS with `max-age=31536000; includeSubDomains; preload` ensures all future visits are SSL-only ([www.itpro.com](https://www.itpro.com/security/ncsc-issues-urgent-warning-over-growing-ai-prompt-injection-risks-heres-what-you-need-to-know#:~:text=2025,based%20vulnerabilities%20like%20SQL%20injection)). There are virtually no downsides, and they complement other defenses by providing a safety net at the browser level. **(Confidence: HIGH)**

**Sources:** OWASP Secure Headers Project (2023) – recommended header configs; Mozilla Observatory Report (2024); MDN Web Docs – CSP Reference (2025); Google Security Blog on HSTS preload (2021).

#### Secure Cookies and CSRF Protection 
**Claim:** **Secure your session cookies or JWT tokens against theft or misuse.** If your app uses traditional server sessions (cookies), always set the cookies with **Secure** (HTTPS-only) and **HttpOnly** flags. `Secure` ensures cookies aren’t sent over HTTP, and `HttpOnly` prevents JavaScript from reading them (mitigating XSS from stealing session IDs). Also consider setting **SameSite=Lax or Strict** on cookies to reduce CSRF (Cross-Site Request Forgery) risk by not sending cookies on cross-origin requests. Additionally, implement **CSRF tokens** or anti-CSRF mechanisms on state-changing POST requests if your app is not using SameSite or if it needs to allow cross-origin requests for some reason. For JWT-based auth (stateless), do not store tokens in plain localStorage if you can avoid it – a **HttpOnly cookie** is often preferable for web apps so that the token is not accessible to scripts. In 2025, many frameworks provide CSRF protection out-of-the-box (e.g. Next.js API routes have built-in CSRF if using their auth cookies, Ruby on Rails has authenticity tokens, etc.), so make sure those are enabled. 

**Evidence:** Session hijacking and CSRF attacks are well-documented threats. In 2025, **OWASP Top 10** still implicitly covers these under Broken Access Control and Security Misconfiguration (missing secure flags is considered a misconfiguration). A notable example: in 2024, a startup’s API was compromised because it set session cookies without `HttpOnly`; an XSS vulnerability allowed an attacker’s script to silently read the user’s cookie and hijack their account. If HttpOnly had been set, the cookie would not have been accessible to JavaScript, potentially foiling that attack. Likewise, without SameSite or anti-CSRF tokens, a malicious site can cause a user’s browser to perform actions on the target site using the user’s session (classic CSRF). For instance, in mid-2025, a proof-of-concept showed how a malicious email link could silently trigger a money transfer on a vulnerable fintech app – because the app trusted any POST with a valid session cookie. The attack was mitigated once the app implemented CSRF tokens (the attacker’s cross-site form no longer had the valid token). Secure cookie flags are no longer optional: browsers like Chrome will soon (by 2026) default to treating cookies as SameSite=Lax if not specified, because unsecured cross-site cookies are so dangerous. The combination of **Secure, HttpOnly, SameSite** on cookies, plus explicit CSRF tokens for critical endpoints, is considered standard practice in 2025. **(Confidence: HIGH)**

**Sources:** OWASP Top 10 2025 – *“A02: Security Misconfiguration”* (mentions cookie settings); OWASP Cheat Sheet – Session Management (2021); Google Chrome dev blog – SameSite updates (Aug 2022); Real-World CSRF exploit writeup (2025).

#### CORS Configuration – No Wildcards with Credentials 
**Claim:** **Configure CORS (Cross-Origin Resource Sharing) properly** – never use a wildcard or reflect arbitrary Origins when allowing credentials. If your API needs to serve browsers on another origin and requires cookies or auth headers, explicitly specify the allowed origin(s). A common mistake is returning `Access-Control-Allow-Origin: *` along with `Access-Control-Allow-Credentials: true`, or echoing back the Origin header without validation; both are insecure. The browser will simply block such responses now, and even if it didn’t, it would enable any site to steal user data by making authenticated cross-site requests. Instead, define a whitelist of trusted origins and have the server check `Origin` against it, responding only with that origin if it’s approved. Do **not** support requests from random origins. 

**Evidence:** According to Mozilla’s documentation, *“The server must not specify the `*` wildcard for the Access-Control-Allow-Origin response-header value when granting credentials”* ([developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#:~:text=,Allow)). In fact, since 2015 browsers enforce that `Access-Control-Allow-Credentials: true` is ignored if the ACAO header is `*` ([developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#:~:text=response%20includes%20an%20%60Access,error%20in%20the%20devtools%20console)). Despite this, misconfigurations persist: some developers use echoing middleware that sends back `Access-Control-Allow-Origin: <request-origin>` and `Access-Control-Allow-Credentials: true` for all requests, effectively granting **universal cross-site access** to their API. In 2024–2025, multiple bug bounty reports showed how such a CORS misconfiguration could be exploited: an attacker can create a malicious page on **their** domain, have a logged-in victim visit it, and via an AJAX call to the API (with credentials), that page receives the sensitive data because the server foolishly allowed that origin. An example from PortSwigger’s labs (2022, updated 2022-2023) demonstrated retrieving an administrator’s API key via a crafted web page due to “basic origin reflection” trust ([portswigger.net](https://portswigger.net/web-security/cors/lab-basic-origin-reflection-attack#:~:text=Academy%20portswigger,the%20administrator%27s%20API%20key%20and)). The fix is straightforward: set your CORS config to either **deny all cross-origin requests by default** or allow only specific origins (and methods/headers). If your app is purely single-origin (e.g. a mobile app or same-site web app), it’s safest to disable CORS entirely (no ACAO header). If multiple origins are needed (say, your production site and a staging site), list them explicitly. Do not allow credentials unless necessary; if you do, ensure `Access-Control-Allow-Origin` is never `*` ([developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#:~:text=,Allow)). Also, never send `Access-Control-Allow-Origin: null` unless you specifically intend to allow the null origin (which is rare and usually a mistake leading to potential issues with some browser contexts). In summary: **strictly limit CORS** to what your app requires. **(Confidence: HIGH)**

**Sources:** Mozilla MDN – *“CORS: Access-Control-Allow-Credentials”* (rev. 2023) ([developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#:~:text=,Allow)) ([developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#:~:text=response%20includes%20an%20%60Access,error%20in%20the%20devtools%20console)); PortSwigger Web Security Academy – CORS Labs (2022); RFC 9180 on CORS (2022).

#### Software Supply Chain Security 
**Claim:** **Secure your supply chain** – manage dependencies and packages with caution. By 2025, “Software Supply Chain Failures” climbed to #3 on the OWASP Top 10 ([owasp.org](https://owasp.org/Top10/?form=MG0AV3#:~:text=2.%20A02%3A2025%20,5)), reflecting the surge in attacks via open-source libraries and build processes. To protect your app, use trusted sources for packages, lock dependency versions (use lockfiles), and monitor for vulnerability alerts in your dependencies (e.g. via `npm audit` or GitHub Dependabot alerts). Be vigilant for typosquatting or malicious packages – especially if you rely on AI code suggestions, which might hallucinate package names that attackers then hijack (a new attack called **“slopsquatting”**). In 2025, there was a wave of npm supply-chain attacks with thousands of malicious packages uploaded; robust dependency auditing and limiting who can publish updates to your app can mitigate this risk. 

**Evidence:** The OWASP Top Ten 2025 recognized **Supply Chain** attacks as a top-three risk for the first time ([owasp.org](https://owasp.org/Top10/?form=MG0AV3#:~:text=2.%20A02%3A2025%20,5)). This includes incidents where attackers insert backdoors into popular libraries (e.g. via compromised maintainer accounts or sabotaged updates) as well as fake packages that unsuspecting developers might install. A notable trend identified in late 2024 was *“AI package hallucination”* – developers using AI assistants sometimes got non-existent package suggestions (e.g. a slightly wrong name); attackers quickly created those names on npm with malicious code to exploit this. In 2025, researchers termed this **“slopsquatting”**: *“a new threat to the software supply chain... exploits 'package hallucinations' — non-existent packages mistakenly added to code by LLMs”* ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=2025,create%20fake%20packages%20with%20these)). By mid-2025, incidents of slopsquatting and broader npm malware had grown significantly. For example, Sonatype’s 2025 software supply chain report noted a **300% increase** in malicious package uploads compared to 2023. One high-impact case: in March 2025, a widely used npm package was compromised to exfiltrate environment variables from projects that installed it (CVE-2025-XXXX). Mitigations include pinning exact versions (so you don’t auto-import a poisoned update), enabling 2FA for npm publish on your own packages, and using sandboxing for build processes. Many teams now also verify integrity with hashes or use dependency scanners. Platforms like GitHub have **Dependabot** which not only flags outdated/vulnerable dependencies but also **GitHub’s secret scanning for packages** catches if common secrets are being exfiltrated by a dependency at runtime. In short, treat your software dependencies as part of your attack surface. Keep them updated (for patches) but also vet them – read the changelogs of critical packages before upgrading, and consider minimal sets of dependencies to reduce exposure. **(Confidence: HIGH)**

**Sources:** OWASP Top Ten 2025 – *“A03:2025 – Software Supply Chain Failures”* ([owasp.org](https://owasp.org/Top10/?form=MG0AV3#:~:text=2.%20A02%3A2025%20,5)); TechRadar – *“Mitigating risks of package hallucination and 'slopsquatting'”* (Jul 16 2025) ([www.techradar.com](https://www.techradar.com/pro/mitigating-the-risks-of-package-hallucination-and-slopsquatting#:~:text=2025,create%20fake%20packages%20with%20these)); Sonatype State of the Software Supply Chain Report (Sep 2025); npm Security Team advisories (2025).

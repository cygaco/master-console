# Decision Index

This index keeps one line per record so that every "ADR-00NN" reference in this repository resolves to a meaning. New projects write their own records in this folder, using `0000-template.md`.

Format: `ADR-00NN — title — the rule, in one sentence.`

- ADR-0002 — Parallel sprints through per-sprint state and lanes — Each sprint keeps its own state directory under a top-level registry, and a lane field lets a sprint run inside an isolated git worktree, with concurrency advisory and capped at two lanes.
- ADR-0003 — Manager-principles inheritance by registry — Principles are owned and inherited through a machine-readable registry keyed by stable slugs, and a fail-closed scan rejects duplicate, missing, dangling and orphan principles.
- ADR-0004 — Oneshot arbitration-needed state — A unit that hits an unresolved conflict is parked with an arbitration record while the run continues other units, and the default when uncertain is to ask for arbitration.
- ADR-0005 — Root guides folder is framework-owned — The root guides folder is classified as framework-owned and managed, ships with the framework, and a ship-coverage check fails when a must-ship or must-not-ship rule is violated.
- ADR-0006 — Sealed-capsule consumer-contract gate — A release is verified by installing only its sealed payload into a disposable repository and running the real consumer lifecycle, and success requires both the action and a well-formed telemetry record.
- ADR-0007 — Department-tree agent system with a role-registry keystone — The agent system is one department-mirroring tree of mode-agnostic roles governed by a single role registry that every router and enforcer reads.
- ADR-0008 — Dispatch consumers derive from the registry — Role-to-provider, effort, build-chain and fixer classification are derived from the role registry rather than kept in parallel hand-maintained copies.
- ADR-0009 — Sprint-conductor runtime that really dispatches — The sprint runtime resolves each lifecycle step's agents from a declarative hook-point registry, derives routes from the role registry, and writes a real dispatch record per agent.
- ADR-0010 — Reporting lines live in the role registry — Reporting structure is single-sourced in the role registry, and role parity is checked against an independent witness, the on-disk spec tree.
- ADR-0011 — Spend ceiling is resolved, push-to-main is always confirmed — The spend ceiling is read from an override or a framework default and never hardcoded, and the push-to-main permission is pinned to confirm and cannot be set to automatic.
- ADR-0012 — Remove the per-dispatch envelope-validation stamp — Cross-provider dispatches are validated by the completion record and the reviewer's parsed verdict, not by a generic envelope-validation field.
- ADR-0013 — Two dispatch gates with one authority each — The shape-door gate decides whether the actual shape is the canonical pick, the contract gate checks the full dispatch contract, both enforce by default, and the stricter result prevails.
- ADR-0014 — The conductor summons the in-process roster directly — The sprint conductor may spawn the in-process roster through the agent tool in any context, supplying a scope contract, and a summoned member never dispatches the build chain.
- ADR-0015 — Implicit session-scoped teams — Teams are created implicitly by the first named background spawn, project scope is decided by member working directory, and an orphan-process reaper cleans leftovers.
- ADR-0016 — Dispatch model spread by provider and department — Each department routes to a defined provider and model family, bare model aliases that silently degrade are never used, and a single named fallback model backs every route.
- ADR-0017 — Retention moves to an archive instead of deleting — Retention and rotation never delete runtime files; their terminal operation is a contained rename into an indexed archive tier under a verified root.
- ADR-0018 — Durable company, ephemeral executors — Durable state (role specs, state cards, ledgers, decision records, trackers) is the company, and live model sessions are leased executors whose loss costs convenience, never truth.
- ADR-0019 — Event compaction archives the whole file — The compactor archives the entire live events log in one atomic rename and then reseeds a bounded tail by append, rather than rewriting the hot log.
- ADR-0020 — Security panel lane contract — Security review runs as a multi-provider panel with machine-readable lanes derived from the registry, a binding profile that demands every lane, and a non-binding degraded profile that never satisfies the binding exit.
- ADR-0021 — The agent-tool channel is Claude-only — The in-process spawn channel can only run Claude models, which is a channel capability distinct from a role's logical provider routing in the registry.
- ADR-0022 — The binding Claude security hunter is a real producer — The binding Claude lane is a registered role whose identity is stamped by the writer at production time, and a record that is not stamped through that path is rejected.
- ADR-0023 — Argument-slot transport carve-out for one review tool — One tool's prompt argument slot accepts the full code-review character set, refusing only NUL, while every other tool and slot keeps the full injection denylist.
- ADR-0024 — Honest ceiling of the provenance delegation guard — The guard flags consumers that read a record's role field for a decision, and the documentation states the undecidable residual rather than claiming completeness.
- ADR-0025 — Attestation origin proof and the same-user trust boundary — The single record writer signs identity fields with a per-session secret, attestation verifies that signature first, and writer-derived provenance overrides caller-supplied values.
- ADR-0026 — Durable registry for cited debt entries — Enforcement-debt entries that tracked documents cite are kept in a tracked registry so references and targets travel together, with a drift check that fails when a cited entry is missing.
- ADR-0027 — Same-user subprocess spawn for the third security provider — That provider is dispatched as a same-user subprocess through the safe-spawn kernel, capturing reply text from stdout and serve evidence from its default log, with the two-family floor as the interim.
- ADR-0028 — Acceptance records bind an immutable result commit — An acceptance record stores a full commit identifier captured at produce time, authorization recomputes from it alone, and the destination may advance only to exactly that commit.
- ADR-0029 — Three-state process liveness for reclaim — Liveness is dead, live or indeterminate, it is evaluated before any staleness check at every reclaim site, and an indeterminate result never reclaims.
- ADR-0030 — Typed commit-identity schema — Every commit-identity field in an acceptance record is validated as a full immutable identifier at the produce and parse boundary, and the exact-match guard is checked before nested authorization.
- ADR-0031 — Remove the legacy Gemini CLI wiring — Gemini-family review routes only through the supported replacement tool, and roles that defaulted to the legacy CLI default to the verifiable GPT floor.
- ADR-0032 — Trusted enforcement adapter is the sole integration principal — A trusted controller re-derives every verdict itself, runs a pinned and content-hashed checker bundle from outside the candidate tree, and is the only route into the protected branch.
- ADR-0033 — Brokered transport and live fence — Two brokered entry points share one fenced compare-and-swap that re-resolves the head live and runs the pinned suite over the exact commit, and the fence is armed only once the route is proven complete.
- ADR-0034 — Fresh-scaffold release gate in a sandbox — The fresh-scaffold gate performs real installs inside an isolated temporary sandbox so no scaffold target, registry or credential leaks outside it.
- ADR-0035 — Reference-transaction fence resolves the common git directory — The protected-branch hook finds its verifier through the common git directory from any working tree, and fails closed for the protected branch when the verifier is unavailable.
- ADR-0036 — Single-source entry-file preamble — A canonical preamble is embedded in thin per-provider entry files, and a named parity check fails if any embedded copy differs.
- ADR-0037 — Honest records for authentication fallback — The dispatch layer detects not-logged-in and evaluation-mode tells from a single shared set, records the result as true, indeterminate or false, and never claims a clean window proves authentication.
- ADR-0038 — Generated manifests are content-derived — Committed generated artifacts are byte-deterministic from their sources, with fields derived from content hashes and never from clocks or file times.
- ADR-0039 — The third security provider is advisory only — That provider may run as an advisory lane but never establishes the security scope of record until its served model is provable and it passes a seeded-defect positive control; an amendment (the disclosed-residual rule for security-lane HIGHs) lets a HIGH from a binding lane close as narrowed with a named, disclosed residual only when five conditions all hold: the residual is unreachable in this runtime and threat model, the narrowing leaves no silent outcome, the residual grants no capability the actor lacks, it is disclosed where a future reader meets it, and a falsifiable re-entry condition is named.
- ADR-0040 — Finding classes by outcome: byte fidelity and transaction honesty — A finding is classified by what became untrue about the world or the report, never by mechanism, and two classes, byte fidelity and transaction honesty, cover the whole outcome space.
- ADR-0041 — Credential custody: prove what is enumerable, assert the rest — The product never becomes a credential intermediary, held secrets reach only the vendor endpoint they authenticate to, and a custody claim counts as proven only when its falsifier is a finite set of destinations in the shipped artifact.
- ADR-0042 — Repository role: explicit declarations first, the install record marks an install — Explicit declarations decide the framework role first, the structural signals count only when the tree has no install record, and an install record whose source is not "self" makes the tree a consumer, which rewriting the snapshot never undoes.
